## 확정된 책임 경계

| 구분 | 담당 영역 | 생성하는 결과 | 하지 않는 일 |
| --- | --- | --- | --- |
| 조건 판정 | Java 도메인 | `일치`, `불일치`, `확인 필요`, `해당 없음`, 필수·우대 조건 일치율 | LLM 추론, 개인정보 검사, 의미 유사도 계산 |
| 의미 유사도 | Python 서비스 | 주요 업무·기술·프로젝트의 항목별 유사도와 근거 | 필수조건 충족 여부와 조건 일치율 확정 |
| 가드레일 | Java–Python 입출력 경계 | 스키마, 허용 필드, 개인정보, 요청 식별자와 원문 근거 검증 결과 | 조건 점수와 유사도 생성·변경 |
| 오케스트레이션 | Java Service와 Worker | 작업 생성, 실행 순서, 부분 완료, 실패와 상태 전이 | 조건 규칙을 HTTP 코드나 Worker에 직접 구현 |

다음 규칙을 함께 적용한다.

- 가드레일 통과는 조건 `일치`를 의미하지 않는다.
- 가드레일 실패는 조건 `불일치` 또는 0점을 의미하지 않는다.
- 스키마 위반, 허용되지 않은 개인정보와 요청에 없는 근거는 검증 실패로 처리하고 조건 판정 입력에서 제외한다.
- 정보 부족이 형식 또는 보안 위반이 아니라면 가드레일 실패로 만들지 않고 Java 도메인의 `확인 필요` 또는 `해당 없음`으로 처리한다.
- 조건 판정과 유사도가 생성된 뒤 가드레일과 LLM 설명은 수치, 상태와 필수조건 충족 여부를 변경할 수 없다.

## 채용공고 분석 우선순위

채용공고의 직무 의미를 분석할 때 다음 순서를 사용한다.

1. 주요 업무
2. 자격요건
3. 우대사항
4. 별도 기술 스택

별도 기술 스택은 공고에 있을 때만 사용한다.
별도 항목이 없으면 주요 업무, 자격요건과 우대사항에서 기술 후보를 추출할 수 있지만 다음 정보를 함께 보존한다.

- 원문 기술명과 정규화 후보
- 기술을 찾은 원문 영역
- 원문 근거 식별자
- 필수, 우대, 언급 없음 또는 판단 불가 상태

주요 업무에서 발견한 기술은 업무 유사도의 근거로 사용할 수 있다.
공고가 해당 기술을 필수 또는 우대로 명시하지 않았다면 조건 판정 항목으로 승격하지 않는다.
Python이 반환한 필수·우대 구분은 근거가 연결된 구조화 후보이며 Java의 최종 조건 판정이 아니다.

## 조건 판정과 조건 일치율

Java 도메인은 다음과 같이 명확하게 비교할 수 있는 조건을 판정한다.

- 신입·경력과 경력 기간
- 학력
- 필수·우대 자격증
- 필수·우대로 명시된 기술
- 근무 지역
- 고용 형태
- 지원 마감일

사용자 데이터 상태는 `보유`, `미보유`, `미입력`으로 구분한다.

| 조건 결과 | 의미 | 점수 반영 |
| --- | --- | --- |
| `일치` | 회사 요구와 사용자 근거가 일치함 | 1점 |
| `불일치` | 회사 요구가 있고 사용자가 미보유함 | 0점 |
| `확인 필요` | 사용자 또는 공고 정보가 부족함 | 제외 |
| `해당 없음` | 회사가 해당 항목을 명시하지 않음 | 제외 |

```text
조건 일치율 = 일치한 비교 항목 수 / 비교 가능한 항목 수
```

비교 가능한 항목은 `일치` 또는 `불일치`로 판정된 항목만 포함한다.
`확인 필요`와 `해당 없음`은 분모와 분자에서 모두 제외한다.
필수조건 일치율과 우대조건 일치율은 별도로 계산한다.

- 필수조건이 하나라도 명확하게 `불일치`이면 `필수조건 불충족`으로 표시한다.
- 우대조건의 `불일치`는 지원 불가로 처리하지 않고 `선택적 보완`으로 표시한다.
- 조건 일치율은 합격 점수나 합격 확률이 아니다.
- 주요 업무·기술·프로젝트의 의미 유사도는 조건 일치율에 포함하지 않는다.
- 조건 일치율과 의미 유사도를 하나의 불투명한 총점으로 합치지 않는다.

## 처리 흐름

```text
채용공고와 사용자 자료
→ Python 정보 추출
→ Python 입력·출력 가드레일
→ Java 계약·식별자·근거 가드레일
→ Java 도메인 조건 판정
→ Python 주요 업무·기술·프로젝트 의미 유사도
→ Java 오케스트레이션 결과 결합
→ 확정 수치를 변경하지 않는 설명 생성
```

Python 추출 결과가 가드레일을 통과하지 못하면 Java 조건 판정을 실행하지 않는다.
가드레일은 오류 또는 격리 사유를 반환하고, Java 오케스트레이션은 작업을 실패 또는 부분 완료로 기록한다.

## MVP 사용자 자료 입력 정책

### 이력서

- 사용자는 텍스트 기반 PDF 이력서를 업로드한다.
- Java는 PDF 형식, 파일 크기와 안전성을 검사하고 Python은 문서의 텍스트와 구조화 항목을 추출한다.
- 추출 결과는 확정 프로필이 아니라 수정 가능한 후보 데이터로 제공한다.
- 사용자가 추출 결과를 확인·수정하고 확정한 뒤에만 조건 판정과 의미 유사도 분석에 사용한다.
- 텍스트를 읽을 수 없는 스캔 PDF는 OCR이나 추측으로 보완하지 않고 `지원하지 않는 문서` 또는 `추출 실패`로 처리한다.
- 스캔 PDF OCR, DOCX, HWP·HWPX와 외부 문서 링크 입력은 MVP 범위에서 제외한다.
- 별도 보관 동의와 보관 기간이 확정되지 않았으므로 원본 PDF는 추출과 안전 검사에 필요한 임시 자료로 취급한다. 구조화 결과, 최소 근거, 출처와 문서 버전만 보관한다.

### 프로젝트

- 사용자가 분석할 공개 GitHub 저장소 URL을 직접 선택해 등록한다.
- 시스템은 저장소 변경을 주기적으로 감지하지 않고 웹훅, 자동 새로 조회, 자동 재분석과 자동 프로필 변경을 실행하지 않는다.
- 최초 등록과 이후 `새로 조회`는 사용자의 명시적인 요청으로만 실행한다.
- 새로 조회할 때 현재 기본 브랜치의 저장소 버전을 이전 조회 버전과 비교한다. 버전이 같으면 `변경 없음`을 반환하고 새 프로젝트 후보와 프로필 버전을 만들지 않는다.
- 저장소 버전이 다르면 조회 시각과 저장소 버전을 연결한 새 출처 스냅숏과 프로젝트 후보를 만들고, 사용자가 확인·수정하고 확정한 경우에만 새 사용자 프로필 버전에 반영한다.
- 이전 출처 스냅숏, 프로필 버전과 분석 결과는 당시 사용한 저장소 버전 기준 이력으로 보존한다.
- Java는 `github.com` 저장소 URL, 공개 접근 가능 여부와 허용된 읽기 범위를 검증한다.
- GitHub 연동은 읽기 전용이다. 저장소 수정·푸시, 코드 실행, 의존성 설치, 임의 외부 URL 조회, 사용자 프로필 전체 또는 선택하지 않은 저장소 탐색을 허용하지 않는다.
- 비공개 저장소, OAuth와 개인 액세스 토큰 입력은 MVP 범위에서 제외한다.
- Java는 검증한 README, 프로젝트 설명과 허용된 최소 파일 내용에 출처 URL, 조회 시각과 저장소 버전을 연결해 Python에 전달한다.
- Java는 사용자가 프론트엔드에서 선택한 기술 스택 태그를 같은 저장소 자료와 함께 전달한다.
- Python은 선택된 기술을 기준으로 저장소 자료에서 기술 근거와 `PROJECT_RESPONSIBILITY`(프로젝트 담당 업무) 후보를 추출한다.
- Python은 전달받은 최소 자료만 분석하며 GitHub URL을 직접 조회하지 않는다.
- 저장소에서 추출한 기술과 역할은 프로젝트 전체의 구조화 후보다. 사용자의 참여 여부, 개인·팀 프로젝트 구분, 직접 담당 역할과 직접 사용한 기술은 사용자가 확인하기 전까지 확정하지 않는다.
- 추출 후보는 사용자의 직접 담당 업무로 확정하지 않고 사용자 확인 전까지 `UNCONFIRMED`(미확정)로 유지한다.
- Java–Python 전달 형태는 [프로젝트 담당 업무 근거 추출 계약](../contracts/project-responsibility-extraction.md)을 따른다.

#### 확정된 프로젝트 추출 정책

- README·프로젝트 설명과 함께 매니페스트, 설정, 선택 기술 관련 핵심 소스·테스트 파일을 제한적으로 사용한다.
- 비밀 설정, 빌드 결과물, 바이너리와 대용량 파일은 제외하고 코드 실행과 의존성 설치를 허용하지 않는다.
- 선택 기술의 근거를 찾지 못하면 오류나 미보유가 아니라 `NEEDS_REVIEW`(확인 필요)로 반환한다.
- 선택하지 않은 기술은 사용자 기술로 자동 추가하지 않는다.
- Java가 GitHub를 조회·검증하고 Python은 전달받은 최소 자료만 분석한다.
- 사용자는 후보를 확인, 수정 후 확인 또는 거부하며 확인된 후보만 의미 비교에 사용한다.
- 미확정 후보는 30일 보관하고 확정 근거는 프로필 버전과 연결하며, 거부 후보 원문은 삭제한다.
- 사용자 기술은 최대 30개이며 Python 한 요청에는 최대 10개를 전달하고 Java가 결과를 합친다.
- README 최대 3개, 매니페스트 최대 20개, 설정 최대 10개, 관련 소스·테스트는 기술당 최대 3개이며 전체 파일은 최대 30개다.
- 개별 원격 파일은 102,400바이트, 전달 구간은 파일당 2,000자, 요청 전체 텍스트는 20,000자로 제한한다.
- 제한 초과 파일은 제외 사유를 기록하고 근거 부족은 `NEEDS_REVIEW`로 처리한다.
- 사용자는 후보를 확인, 수정 후 확인 또는 거부하며 결정에는 후보 버전을 사용한다.
- 확정·거부 상태는 최종 상태이고 같은 결정 재전송만 멱등하게 허용한다.
- 후보 API의 권한, 404·409·410 처리는 공유 계약을 따른다.

### 현재 구현과의 차이

- 현재 `POST /api/v1/documents`는 `documentType`과 `text`를 받는 JSON 임시 API다.
- `POST /api/v1/project-sources/github`는 사용자가 선택한 공개 GitHub 저장소를 검증하고 정규 URL, 기본 브랜치와 현재 `commitSha`를 현재 사용자 소유의 `ProjectSource`로 등록한다.
- GitHub 주소 오류, 저장소 확인 실패, 요청 제한과 외부 서비스 장애는 각각 400, 404, 429와 503으로 구분한다.
- PDF 업로드, 파일 안전 검사, 추출 결과 수정·확정, GitHub 새로 조회와 프로젝트 후보 확정은 아직 구현되지 않았다.
- 다음 구현을 시작하기 전에 PDF 등록·추출 결과·사용자 확정과 GitHub 새로 조회 상태의 요청, 응답, 오류와 보관 정책을 먼저 확정해야 한다.

## 계층별 코드 배치 기준

### Java

| 계층 | 책임 | 대표 위치 |
| --- | --- | --- |
| API | 사용자 HTTP 요청·응답 | `controller`, 외부 API DTO |
| 애플리케이션·오케스트레이션 | 유스케이스, 트랜잭션과 작업 실행 | `service`, `pythonworker` |
| 도메인 | 조건 판정, 조건 일치율과 상태 전이 정책 | `domain` |
| Python 연동 | 내부 HTTP 호출과 경계 검증 | `client`, Python 계약 DTO, `guardrail` |
| 저장 | 분석 작업과 결과 영속화 | `repository`, `entity` |

`pythonworker`는 독립 계층이 아니다.
저장된 분석 작업을 실행하는 애플리케이션·오케스트레이션 컴포넌트이며 Python HTTP 세부 구현은 `PythonAiClient`에 둔다.

### Python

| 영역 | 책임 |
| --- | --- |
| `api/` | Java 내부 요청 수신과 HTTP 응답 |
| `schemas/` | Java–Python 요청·응답과 모델 출력 스키마 |
| `services/` | 추출·분류·유사도·설명 생성 유스케이스 |
| `providers/` | Ollama·Gemini·임베딩 모델 호출 |
| `guardrails/` | 입력 허용 필드·개인정보와 출력 스키마·근거 검사 |

Python `services`는 LLM 전용 계층이 아니다.
코사인 유사도, 입력 분할과 결과 조합처럼 LLM을 직접 호출하지 않는 온라인 분석 로직도 포함할 수 있다.

온라인 요청을 처리하는 `app/`과 오프라인 모델 개발 영역인 `training/`, `evaluation/`은 분리한다.
운영 FastAPI 요청은 학습과 평가 작업을 직접 실행하지 않는다.

## 현재 구현 상태

2026-07-27 기준으로 이 문서의 책임 경계는 정책과 설계로 확정했지만 관련 기능 전체가 코드로 구현된 상태는 아니다.

- Java 도메인에는 현재 사용자 문서 모델과 문서 종류·등록 상태가 구현되어 있다.
- 조건 판정, 필수·우대 조건 일치율과 분석 결과 결합 도메인은 아직 구현되지 않았다.
- Java–Python 조건 판정 및 유사도 계약 enum과 JSON 필드는 아직 확정·구현되지 않았다.
- Python 프로젝트에는 기본 FastAPI 애플리케이션과 상태 확인 테스트가 있으며 문서의 전체 계층 폴더는 아직 구현되지 않았다.
- `training/`과 `evaluation/`은 구현 예정 구조이며 현재 완료된 기능으로 표시하지 않는다.
- 결과 등급과 정렬 가중치는 테스트 자료와 측정 기준이 없으므로 확정하거나 구현하지 않는다.
- 현재 문서 등록 API는 JSON 텍스트만 받고 있으며 PDF 업로드와 추출 결과 수정·확정은 구현되지 않았다.
- 공개 GitHub 저장소 최초 등록과 현재 `commitSha` 저장은 구현됐지만 새로 조회, 변경 비교, 후보 생성과 프로필 확정은 구현되지 않았다.

- `repository_evidence.py`는 Python이 GitHub 저장소를 직접 조회하므로 Java가 최소 자료를 전달한다는 현재 문서 및 제안 계약과 일치하지 않는다.
