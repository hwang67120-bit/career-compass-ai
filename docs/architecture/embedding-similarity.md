# 임베딩과 의미 유사도

> **결론부터**: 임베딩은 MVP에서 제외했다(아래 2026-08-11 결정). 이 문서는 그 판단 근거가 된 실험 기록이다.

## 목적과 범위

이 문서는 "벡터를 어떻게 만들고 어떻게 비교하는가"를 정의한다. 벡터를 어디서 검색하고 어떤 순서로 후보를 추릴지는 다루지 않는다.

## 임베딩 생성 원칙

- 사용자 경험, 직무, 업무, 기술, 공고와 회사 설명을 의미 비교에 쓸 벡터로 변환한다.
- 결과에는 항상 다음을 함께 포함한다: 사용한 모델 이름, 전처리 방식, 벡터 차원, 생성 버전.
- 이 정보 없이 벡터만 반환하지 않는다 — 나중에 어떤 모델·버전으로 만든 벡터인지 추적할 수 있어야 한다.

## 유사도 계산 원칙

- **사용자·공고 유사도**: 사용자 경험과 채용 공고의 직무·업무·기술·프로젝트를 항목별로 비교한다. 하나의 뭉뚱그려진 점수가 아니라 항목별 비교 결과를 반환한다.
- **사용자·회사 유사도**: 사용자가 원하는 업무 방향과 회사의 확인된 사업·업무 영역을 비교한다. 회사 유사도와 특정 공고 유사도는 서로 다른 값이며 섞어서 반환하지 않는다.
- **항목별 근거 반환**: 전체 점수만 주지 않고, 어떤 사용자 경험 문장과 어떤 공고 문장이 그 유사도에 영향을 줬는지 연결해서 반환한다. (근거 없는 출력 차단 원칙과 동일한 이유 — [guardrails.md](guardrails.md))

## 계산 방식

- **코사인 유사도**: 같은 임베딩 모델에서 생성된 벡터끼리 방향 유사도를 계산할 때 사용한다.
- **거리 계산(유클리드 거리 또는 내적)**: 선택한 모델·벡터 저장소에서 필요할 때만 사용한다.
- 여러 계산법을 "일단 다 쓰고 보자"는 이유로 동시에 적용하지 않는다. 하나를 선택하고 이유를 남긴다.
- 조건 일치율(Java 도메인)과 의미 유사도(Python)는 서로 다른 값이며, 하나의 불투명한 총점으로 합치지 않는다 — 이건 코덱스의 `docs/analysis-responsibility-boundaries.md`에서도 이미 확정한 원칙이다.

## 오류로 구분해야 하는 경우

다음은 낮은 유사도 점수로 처리하지 않고 별도 오류로 구분한다.

- 비어 있는 입력 항목
- 벡터 차원이 서로 다른 경우
- 서로 다른 모델 버전으로 생성된 벡터를 비교하려는 경우
- 계산 자체가 불가능한 값

## 최소 품질 기준

- 유사도가 최소 기준보다 낮은 후보는 "의미상 관련 있는 결과"로 취급하지 않는다.
- 기준을 충족한 후보가 없으면 빈 결과와 사용한 기준을 함께 반환한다 (근거 없이 억지로 후보를 채우지 않는다).

## 실험 결과 — 로컬 임베딩 모델의 도메인 구분력 문제 (2026-07-28)

가상의 백엔드·프론트엔드·요식업 이력서·채용공고 문단(직접 만든 예시, 실제 개인정보 아님)으로 4가지 조합을 비교했다.

| 실험 | 결과 |
|---|---|
| `nomic-embed-text` + 긴 원문 | 백엔드-프론트엔드 이력서 유사도(0.9720)가 정답 쌍(백엔드 이력서-백엔드 공고, 0.8720)보다 높게 나옴 |
| `qwen2.5`(범용 LLM) + 긴 원문 | 모든 쌍이 0.91~0.96 사이로 뭉쳐서 구분이 거의 안 됨 |
| `nomic-embed-text` + 짧은 키워드 목록 | 모든 쌍이 0.98~0.99로 더 심하게 뭉침 |
| **`gemini-embedding-001` + 긴 원문** | **정답 쌍(0.7788) > 다른 기술직군(0.7019) > 완전 무관(0.5807~0.6553) 순서로 정확히 구분됨** |

배치로 여러 텍스트를 같이 넣어도 개별 벡터가 달라지지 않는 것은 별도로 확인했다 (계산 버그가 아님).

**결론**: 로컬 Ollama 계열 임베딩(`nomic-embed-text`, 그리고 임베딩 전용이 아닌 `qwen2.5`)은 이 프로젝트의 한국어 이력서·채용공고 도메인에서 비슷한 직무끼리 구분하는 능력이 낮았다. Gemini의 `gemini-embedding-001`(3072차원)만 기대한 순서대로 구분했다. 그래서 `app/providers/embedding.py`에 두 provider를 모두 구현해뒀다. 다만 MVP는 임베딩을 빼고 LLM-as-judge로 갔고(아래 결정), 임베딩을 다시 쓴다면 제대로 구분한 건 Gemini뿐이었다.

이 실험은 표본이 6~8개 문장 수준으로 작아 정식 평가([training-data-standards.md](training-data-standards.md) 기준의 골드 데이터)는 아니다 — 정식 결론이 아니라 다음 모델 선정 논의의 출발점으로만 쓴다.

## MVP 결정 — 임베딩 호출 제외, 분석 모델 유지 (2026-08-11)

MVP 분석 경로에서는 Ollama·Gemini 임베딩 생성과 코사인 유사도 계산에 토큰·실행 자원을
사용하지 않는다. 기존 임베딩 코드와 환경변수는 실험 재현용으로 남기며 운영 분석에서는
호출하지 않는다.

Gemini API나 분석 기능을 제거하는 결정은 아니다. Ollama와 Gemini는 채용공고 추출과 근거
기반 LLM 분석에 집중한다. Ollama를 기본 Provider로 사용하고 Gemini는 실패 시 폴백과
제한적인 교차검증에 사용하며 상시 병행 호출은 하지 않는다.

의미 비교는 `LLM_JUDGE`로 갔다. 2026-08-12 합성 fixture 평가에서 qwen2.5가 품질 게이트를
통과했다([job-fit-semantic-similarity.md](job-fit-semantic-similarity.md)).
## 확인 필요

- 실제 사용할 임베딩 모델 — 위 실험 결과상 Gemini가 유력하지만, 더 큰 표본과 정식 평가 자료로 재검증 필요
- 로컬(Ollama) 임베딩을 계속 병행할지, 아니면 임베딩만 Gemini로 통일할지 (메인 LLM은 Ollama 우선 원칙과 별개로 결정 필요)
- 최소 품질 기준의 구체적인 수치
- 벡터 저장 위치 (초기 단순 저장 vs `pgvector` vs 별도 VectorDB) — 노션 의존성 문서에 이미 조건부로 남아 있음, 데이터 규모가 생기기 전까지 미정
