# ADR 0001: 멀티 머신 · 도메인별 병렬 에이전트 개발 구성

상태: 채택 (2026-08-14)

## 배경

혼자 큰 프로젝트(Java 백엔드 + Python AI + 계약 + 배포)를 만들면서 속도가 필요했다. 그래서 바이브 코딩으로 **AI 에이전트를 도메인별로 나눠 병렬**로 굴렸다 — Java는 Codex, Python은 Claude. 각자 담당 범위가 격리돼 서로 안 밟으니 두 작업 스트림이 동시에 나아갔다.

처음엔 이 모두를 윈도우 한 대에 몰아넣었는데, 세 군데서 삐걱댔다.

- **환경변수**: `.env`·내부 토큰·API 키가 늘며 값이 어긋나 연결이 깨졌다.
- **방화벽**: Windows Firewall이 서비스 포트(8000)를 막아 Java→Python 연결이 조용히 실패했다.
- **Docker on Windows**: 내부 Linux VM(WSL2/Hyper-V) 오버헤드로 컨테이너를 올리면 CPU가 급증하고 전체가 렉에 걸려 작업 흐름이 끊겼다.

## 결정

관심사를 자연스러운 자리로 분리한다.

| 머신 | 역할 |
|---|---|
| Linux | Java·컨테이너·서버 성격 (Docker 네이티브라 가벼움 — CPU 문제 직접 해결). 담당: Codex |
| Windows | Python·Ollama·GUI 도구. 담당: Claude |
| 상시 서버(192.168.0.88) | 24/7 검증·CI·AWS 전 스테이징 |

도메인 경계(누가 어느 코드를 건드리나)는 유지하고, 물리적 분리가 에이전트 병렬의 격리를 겸한다. 서버 간 통신은 Tailscale, 인증은 내부 토큰.

## 결과

### 장점
- **병렬 격리**: 에이전트 2대가 다른 머신·다른 도메인 → 충돌 0, 두 스트림 동시 진행 → 빠름.
- **실무형 분산 경험**: Java↔Python이 실제 네트워크로 통신 → 방화벽·바인딩·토큰·타임아웃 문제를 개발 중에 미리 겪음(포트폴리오 가치).
- **중립 검증 지점**: 상시 서버가 로컬 상태에 안 의존하는 제3의 진실 + 배포 리허설.
- **환경·장애 격리**: JVM·Python 의존성 안 섞임, 한 머신 문제나도 나머지 작업 지속.

### 단점
- **운영 복잡도**: 서비스를 머신마다 켜고 연결 확인, 네트워크 설정 지점 증가.
- **drift**: 머신별 코드·env·모델 버전이 어긋날 수 있음.
- **디버깅 난이도**: 문제가 네트워크 경계를 넘으면 원인 격리가 어려움.
- **보안 표면**: 머신 간 통신·서버 노출로 방어 지점 증가.

### 단점 상쇄 (진행 중)
| 단점 | 수단 |
|---|---|
| 하나씩 켜기·확인 | CI/CD (Python 단위 CI 완료, 통합 진행) |
| drift | 매 push CI 검증 → 어긋나면 실패 |
| 디버깅 | 요청ID 로그 추적·헬스체크 |
| 보안 표면 | 공개 repo fork 격리·서버 하드닝 |

배포(compose)까지 가면 머신 분리는 논리적으로만 남고 조작 부담은 대부분 사라진다.

## 메모
이 구성은 설계로 먼저 정한 게 아니라 **단일 윈도우의 실제 마찰에서 하나씩 옮겨 푼 결과**다. 병렬 AI 협업이라는 제약에서 나온 것이라 이유가 명확하다.
