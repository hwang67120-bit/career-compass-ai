# ADR 0003: 로컬 vs 호스팅 LLM 선택과 Java·Python 경계

상태: 채택 (2026-08-18)

## 배경

이 프로젝트는 LLM(AI)과 백엔드를 Java·Python으로 나눴다. 채용공고가 회사마다
`Python 기반 LLM`을 명시하기도, `Java/Spring`을 명시하기도 해서 양쪽을 다룰 수 있는
프로젝트로 잡은 배경도 있다.

그런데 스스로 반박해봤다. **"AI니까 Python"이라는 통념은 이 프로젝트에선 성립하지 않는다.**

- ML/DL(학습)은 범위에서 제외했다([ADR 0002](0002-vibe-coding-quality-management.md) 오버엔지니어링 회피).
- 임베딩은 측정 후 거절, Vector DB·RAG는 보류했다. → 파이썬의 특기라던 것들이
  실제로 이 프로젝트엔 거의 없다.
- 완제품 LLM을 API로 호출하는 건 학습이 아니라 **엔지니어링**이고, 그건 Java도 한다.

## 반대논리를 정면으로 (Java로도 된다)

정직하게 인정한다. 순수 추론(inference) 소비만 보면:

- LLM 호출·RAG·임베딩·코사인 유사도는 Java(Spring AI, LangChain4j)로 **충분히 가능**하다.
- 오히려 **계약·타입 검증 가드레일은 Java가 더 낫고, 실제로 이 프로젝트도 Java에 뒀다**
  (`PythonEvidenceSimilarityClient`의 `validate`+`ResponseViolation`).

그래서 "Python이 아니면 안 된다"는 거짓이다. 진짜 이유는 다른 축에 있다.

## 결정 — 축은 "로컬 vs 호스팅 LLM"

핵심 선택은 언어가 아니라 **모델을 어디서 돌리느냐**다.

| | 호스팅(OpenAI·Gemini) | 로컬(Ollama) |
|---|---|---|
| 실행 위치 | 제공사 서버(강력·일관) | 내 GPU(품질 편차 큼) |
| 신뢰성 전략 | 적게 필요 | **많이·섬세하게 필요** |
| 개선 여지 | 못 건드림 | **파인튜닝 가능 → PyTorch** |

이 프로젝트는 비용·프라이버시·통제를 위해 **로컬(Ollama)을 기본으로 택했다.** 그 결과:

- **로컬은 품질이 갈리므로 신뢰성 엔지니어링(재시도·모델 언로드·폴백·근거 검증)이 필요**하고,
  부족하면 **파인튜닝으로 강화할 문이 열려 있다(PyTorch 영역)**. → 이건 Python의 일.
- **결정론적 오케스트레이션·상태·저장·계약 검증**은 Java의 일.
- Gemini는 **호스팅 폴백**으로만 쓰고, 그쪽엔 개인정보 가드레일을 건다.

## 가드레일 비대칭 (경계의 핵심)

가드레일은 한 종류가 아니고, 로컬·호스팅에 따라 **방향이 반대**다. 코드가 이미 이를 반영한다.

| 가드레일 종류 | 더 필요한 쪽 | 구현 위치 |
|---|---|---|
| 신뢰성(재시도·언로드·폴백·근거 검증) | **로컬** — 품질 편차 | Python(`job_posting_extraction.py`) |
| 개인정보 제거(redaction) | **호스팅** — 데이터가 밖으로 나감 | Python, **Gemini 직전에만**(`contact_info_redaction.py`) |
| 계약·타입·식별자 검증 | 경계 무관, 소비 측 | **Java**(`validate`+`ResponseViolation`) |

"호스팅은 가드레일이 덜 필요"는 **신뢰성 축에서만 참**이고, 개인정보 축에선 뒤집힌다.

## 결과

### 근거(실증)
- **로컬이 섬세한 전략을 요구한다는 것을 직접 겪고 문서화했다** — Ollama 세션 오염 조사
  (`docs/current-work.md` 2026-08-03/04): 같은 모델을 안 내리고 연속 처리하면 근거 생성이
  비는 현상을 재현하고, 검증 실패 시 언로드 후 1회 재시도 + Gemini 폴백으로 완화했다.
- 개인정보 redaction은 외부 전송(Gemini) 직전에만 적용하고 로컬 Ollama는 거치지 않는다.

### 장점
- **적재적소**: Java=결정론적 서비스, Python=AI 신뢰성·평가.
- **로컬 선택의 이점**: 비용·프라이버시·오프라인·벤더 독립. 필요 시 파인튜닝 문이 열려 있음.
- **양쪽 스택 시연**: 채용 시장이 요구하는 Python-LLM과 Java/Spring을 한 프로젝트에서.
- 도메인 분리가 병렬 AI 에이전트 개발의 격리를 겸함([ADR 0001](0001-multi-machine-parallel-agent-setup.md)).

### 단점 (정직하게)
- 순수 추론만 필요했다면 Java 단일 스택으로도 됐다 — 경계(계약)를 하나 더 관리하는 비용.
- **파인튜닝은 아직 안 했다** — "가능성(문이 열림)"이지 실적이 아니다.
- provider 2개(로컬·호스팅) 운영으로 설정·장애 지점이 늘어난다.

## 메모

이 분리의 정직한 근거는 "AI라서 Python"이 아니라 **"로컬 LLM을 택했으니 Python"**이다.
ML/DL 특화 논리는 이 프로젝트에선 성립하지 않는다는 점을 숨기지 않는다. 완제품 LLM을
Java로 부를 수 있다는 반대논리도 사실로 인정하고, 그 위에서 로컬 선택이 만든 신뢰성·파인튜닝
필요가 Python을 정당화한다.
