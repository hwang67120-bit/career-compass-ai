# Career Compass AI 공통 용어집

이 문서는 프로젝트 문서와 AI 대화에서 사용하는 영어 기술 용어의 한글 뜻을 정리한다.
코드 식별자·JSON 필드·환경변수·로그 값은 영어 원문을 유지하고, 사람이 읽는 설명에서는
처음 등장할 때 `영어(한글 뜻)` 형식으로 작성한다.

예시:

> Ollama를 기본 `Provider(모델 제공자)`로 사용하고 실패하면 Gemini를
> `Fallback(대체 처리)`로 사용한다.

## 읽기 규칙

- 영어 용어를 한글 번역 없이 단독으로 사용하지 않는다.
- 코드 값은 번역하지 않고 바로 옆에 한글 뜻을 붙인다.
- 같은 개념은 프로젝트 전체에서 같은 한글 표현을 사용한다.
- 약어는 처음 등장할 때 전체 영어와 한글 뜻을 함께 적는다.
- 한글 번역이 기술적으로 부정확해질 때는 영어 원문을 병기한다.

## 서비스와 시스템

| 영어·코드 용어 | 한글 뜻 | 프로젝트에서의 의미 |
|---|---|---|
| Frontend | 프론트엔드·사용자 화면 | 사용자의 입력, 진행 상태와 결과 차트를 표시하는 영역 |
| Backend | 백엔드 서버 | Java API, 인증, 상태·데이터 저장과 조건 판정을 담당하는 영역 |
| API | 프로그램 간 요청·응답 통로 | 프론트–Java 또는 Java–Python 통신 규칙 |
| Endpoint | API 요청 주소 | `/api/v1/...` 같은 하나의 기능 주소 |
| Request | 요청 | 호출자가 서버에 보내는 데이터 |
| Response | 응답 | 서버가 호출자에게 돌려주는 결과 |
| Provider | 제공자·연동 구현 | 공공데이터, Ollama, Gemini처럼 실제 데이터나 모델을 제공하는 대상 |
| Adapter | 변환 연결부 | 외부 형식을 내부 계약에 맞게 바꾸는 컴포넌트 |
| Worker | 백그라운드 작업 실행기 | 대기 중인 분석을 가져와 순서대로 처리하는 Java 컴포넌트 |
| Scheduler | 예약 실행기 | Worker를 일정 주기로 실행하는 기능 |
| Pipeline | 처리 흐름 | 입력부터 추출·판정·저장·화면까지 이어지는 단계 |
| Runtime | 실행 시점 환경 | 실제 서버 요청을 처리하는 환경 |
| Offline | 오프라인 작업 | 운영 요청과 분리된 모델 평가·실험 작업 |

## 데이터와 서버 계약

| 영어·코드 용어 | 한글 뜻 | 프로젝트에서의 의미 |
|---|---|---|
| Contract | 서버 간 계약 | Java와 Python이 합의한 필드·타입·상태·오류 규칙 |
| Schema | 데이터 구조 규칙 | JSON 필드, 타입과 필수 여부 |
| DTO | 데이터 전달 객체 | 서버 계층 또는 서버 사이에서 값을 전달하는 객체 |
| Enum | 선택 가능한 고정값 | 상태·종류처럼 허용된 값만 사용하는 타입 |
| Field | 필드·데이터 항목 | JSON이나 객체 안의 하나의 값 |
| Payload | 전달 데이터 본문 | 요청·응답에서 실제로 주고받는 데이터 |
| Fixture | 반복 테스트용 고정 데이터 | 같은 결과를 재현하기 위해 저장한 합성 공고·응답 |
| Mock | 가짜 연동 구현 | 실제 외부 시스템의 입구만 대신하는 테스트 구현 |
| Source Text | 분석 원문 | 개인정보를 제거하고 Python에 전달하는 최소 공고 문장 |
| Request ID | 요청 추적 식별자 | Java·Python 로그에서 같은 요청을 연결하는 값 |
| Version | 버전 | 분석에 사용한 프로필·공고·근거의 고정 시점 |
| Migration | 데이터베이스 변경 이력 | 테이블·컬럼 변경을 순서대로 적용하는 파일 |
| Flyway | DB 변경 이력 도구 | 데이터베이스 마이그레이션을 관리하는 도구 |

## AI와 의미 분석

| 영어·코드 용어 | 한글 뜻 | 프로젝트에서의 의미 |
|---|---|---|
| AI | 인공지능 | 규칙만으로 처리하기 어려운 구조화·의미 분석 기술 전체 |
| LLM | 대규모 언어 모델 | 문장을 이해하고 구조화 결과를 생성하는 모델 |
| Ollama | 로컬 모델 실행 도구 | 기본 채용공고 추출·분석 Provider |
| Gemini | Google 외부 AI 모델 | Ollama 실패 시 폴백과 제한적 교차검증 Provider |
| Prompt | 모델 지시문 | LLM에 역할, 입력과 출력 규칙을 전달하는 문장 |
| Inference | 모델 추론 실행 | 학습된 모델에 입력을 보내 결과를 얻는 과정 |
| Extraction | 구조화 추출 | 원문에서 직무·업무·필수·우대 기술을 뽑는 과정 |
| Classification | 분류 | 직군·기술·회사 유형을 정해진 종류로 나누는 과정 |
| Normalization | 정규화 | 같은 의미의 여러 표기를 대표 형식으로 정리하는 과정 |
| Embedding | 임베딩·의미 벡터 변환 | 문장을 숫자 벡터로 바꾸는 방식. MVP 분석 경로에서는 사용하지 않음 |
| Vector | 벡터·숫자 배열 | 임베딩 결과를 표현하는 숫자 목록 |
| Cosine Similarity | 코사인 유사도 | 두 벡터의 방향이 얼마나 가까운지 계산하는 값. MVP에서는 제외 |
| LLM-as-judge | LLM 근거 관계 판정 | LLM이 두 업무 근거의 관련 여부를 구조화 값으로 판정하는 후보 방식 |
| Judgment | 판정값 | `RELATED`, `NOT_RELATED`처럼 LLM이 반환하는 고정 결과 |
| Fallback | 실패 시 대체 처리 | 기본 Ollama 실패 시 조건부로 Gemini를 호출하는 방식 |
| Cross-validation | 교차검증 | 다른 모델·자료로 결과가 재현되는지 제한적으로 확인하는 과정 |
| Guardrail | 안전장치 | 허용 필드, 개인정보, 근거와 응답 형식을 검사하는 규칙 |
| Hallucination | 근거 없는 생성 | 입력에 없는 내용을 모델이 사실처럼 만드는 문제 |
| Model Execution | 모델 실행 정보 | 실제 사용한 단계, Provider와 모델 이름 |
| Confidence | 모델 확신도 | 보정 전에는 확률처럼 사용자에게 제공하지 않는 값 |

| Job Requirement | 채용 요구조건 | 기술·경력·학력·자격증·지역·고용 형태 등의 조건 |
| User Profile | 사용자 프로필 | 사용자가 확인한 목표 직무와 기술 정보 |
| Project Source | 프로젝트 출처 | 사용자가 선택한 공개 GitHub 저장소 |
| Evidence | 근거 | 추출·판정 결과를 직접 뒷받침하는 최소 원문 |
| Condition Result | 조건 판정 결과 | Java가 명확한 규칙으로 비교한 결과 |
| Similarity Result | 의미 비교 결과 | Python이 공고 업무와 프로젝트 업무 관계를 분석한 결과 |
| Analysis Result | 최종 분석 결과 | 조건 판정, 의미 비교, 근거와 상태를 합친 사용자 결과 |

## 조건·의미 비교 상태

| 코드 값 | 한글 뜻 | 사용 기준 |
|---|---|---|
| `MATCHED` | 일치 | 공고 조건과 사용자가 확인한 근거가 일치 |
| `MISMATCHED` | 불일치 | 사용자가 해당 조건을 미보유라고 명시적으로 확인 |
| `NEEDS_REVIEW` | 확인 필요 | 사용자 또는 공고 정보가 부족 |
| `NOT_APPLICABLE` | 해당 없음 | 공고가 해당 조건을 명시하지 않음 |
| `RELATED` | 업무 관련 있음 | 공고 업무와 프로젝트 업무가 근거상 관련 있음 |
| `NOT_RELATED` | 업무 관련 없음 | 두 업무가 근거상 관련 없음 |
| `NOT_CALCULABLE` | 계산할 수 없음 | 비교할 근거가 부족해 0점으로 처리하지 않음 |

## 프로젝트 기술 판정·제안 상태

| 코드 값 | 한글 뜻 | 사용 기준 |
|---|---|---|
| `FOUND` | 근거 발견 | 선택 기술과 연결되는 저장소 근거가 확인됨 |
| `NEEDS_REVIEW` | 확인 필요 | 선택 기술의 근거가 부족하며 오류나 미보유로 단정하지 않음 |
| `PENDING` | 결정 대기 | 미선택 기술 제안에 사용자의 결정이 필요함 |
| `ADD` | 추가 | 사용자가 제안 기술을 프로필에 반영하도록 요청 |
| `ADDED` | 추가 확정 | 추가 결정이 저장된 최종 상태 |
| `IGNORE` | 무시 | 사용자가 제안 기술을 프로필에 반영하지 않도록 요청 |
| `IGNORED` | 무시 확정 | 무시 결정이 저장된 최종 상태 |

## 테스트와 완료 기준

| 영어 용어 | 한글 뜻 | 프로젝트에서의 의미 |
|---|---|---|
| Unit Test | 단위 테스트 | 함수·클래스 하나의 규칙을 독립적으로 검사 |
| Integration Test | 통합 테스트 | 데이터베이스나 여러 컴포넌트 연결을 검사 |
| Contract Test | 계약 테스트 | Java와 Python이 같은 요청·응답 규칙을 지키는지 검사 |
| End-to-End Test | 전체 연결 테스트 | 사용자 입력부터 최종 결과까지 전체 흐름 검사 |
| Browser Test | 브라우저 테스트 | 실제 화면에서 사용자 흐름을 확인 |
| Regression Test | 회귀 테스트 | 기존 기능이 새 변경으로 깨지지 않았는지 검사 |
| Smoke Test | 기본 동작 확인 | 서버 실행과 핵심 경로가 즉시 실패하지 않는지 확인 |
| Quality Gate | 품질 통과 기준 | 모델·기능을 채택하기 전에 만족해야 하는 최소 조건 |
